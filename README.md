# Nexus Messenger

Тёмный веб-мессенджер на React, TypeScript, Vite и Supabase. Интерфейс адаптирован для узких и широких экранов.

## Локальный запуск

1. Установи Node.js LTS.
2. Клонируй репозиторий и открой папку проекта.
3. Установи зависимости и запусти dev-сервер:

```bash
npm install
npm run dev
```

Для проверки production-сборки:

```bash
npm run build
npm run preview
```

## Настройка Supabase

Клиент Supabase настраивается в `src/lib/supabase.ts`. Для локального запуска нужны URL проекта и публичный anon/publishable key в переменных окружения, которые ожидает этот файл. Не помещай service-role key в браузерный код.

SQL настраивается в Supabase Dashboard → SQL Editor. Выполняй в следующем порядке:

1. `supabase/schema.sql` — базовые таблицы, триггеры, RLS и Realtime.
2. `supabase/migrations/20261025_unique_usernames.sql` — уникальные имена пользователей.
3. `supabase/migrations/20261026_online_media.sql` — приватный bucket `chat-media`, политики Storage и публикация Realtime.
4. `supabase/migrations/20261027_direct_chats.sql` — безопасное создание личных диалогов.
5. `supabase/migrations/20261028_cloud_group_chats.sql` — облачные группы и безопасные ссылки-приглашения.
6. `supabase/migrations/20261029_persistent_polls.sql` — сохранение опросов и серверная обработка голосов.
7. `supabase/migrations/20261030_poll_and_message_hardening.sql` — защита голосов и сообщений триггерами.
8. `supabase/migrations/20261031_read_state.sql` — RPC `mark_chat_read` и `last_read_at` для непрочитанных и квитанций.
9. `supabase/migrations/20261032_presence.sql` — `profiles.last_seen_at` для «был(а) в сети».
10. `supabase/migrations/20261033_push_subscriptions.sql` — таблица Web Push-подписок для фоновых уведомлений.
11. `supabase/migrations/20261034_group_management.sql` — RPC `set_chat_member_role`, `remove_chat_member`, `rotate_chat_invite`, срок жизни приглашения и триггер `chats_guard_update`, закрывающий смену `created_by`.
12. `supabase/migrations/20261035_message_search.sql` — полнотекстовый поиск: `tsvector`, GIN-индекс и RPC `search_messages`.
13. `supabase/migrations/20261036_pinned_messages.sql` — закреплённые сообщения и RPC `set_message_pin` / `pinned_messages`.
14. `supabase/migrations/20261037_privacy.sql` — блокировки, скрытие «был(а) в сети», отключение квитанций и RPC `delete_my_account`.

Миграции рассчитаны на запуск после базовой схемы. Проверяй результат каждой миграции в SQL Editor. Не отключай RLS и не вставляй секретный service-role key во фронтенд.

## PWA и уведомления

Приложение собирается как PWA: манифест `public/manifest.webmanifest`, иконки в `public/icons` (пересобираются командой `node scripts/generate-icons.mjs`), service worker `src/sw.ts` через `vite-plugin-pwa` в режиме `injectManifest`. GitHub Pages отдаёт статику без SPA-fallback, поэтому маршруты остаются на корне приложения.

Что работает без дополнительных настроек:

- установка на телефон и в десктопный браузер, офлайн-оболочка (precache HTML/CSS/JS);
- бейдж и счётчик в `document.title` по числу непрочитанных (`useUnreadBadge`);
- уведомление при новом сообщении, если вкладка скрыта и разрешение выдано (`useMessageNotifications`);
- пагинация истории: первые 50 сообщений на чат, дальше keyset-подгрузка по `(created_at, id)` при скролле вверх или кнопкой «Загрузить ещё».

Для фоновых Web Push (приложение закрыто) нужен серверный контур:

1. Сгенерировать ключи: `npx web-push generate-vapid-keys`.
2. Положить публичный ключ в `VITE_VAPID_PUBLIC_KEY` (локально и в секреты GitHub Actions).
3. Задеплоить Edge Function: `supabase functions deploy push-notify --no-verify-jwt`.
4. Задать секреты функции: `supabase secrets set VAPID_PUBLIC_KEY=... VAPID_PRIVATE_KEY=... VAPID_SUBJECT=mailto:...`.
5. Добавить Database Webhook на `public.messages` (INSERT) → Edge Function `push-notify`.
6. Нажать в приложении колокольчик «Уведомления» — браузер создаст подписку и сохранит её в `push_subscriptions`.

Без шага 2 колокольчик включает только локальные уведомления открытой вкладки.

## Что уже есть в коде

- Интерфейс чатов, поиск и адаптивная компоновка.
- Подключение Supabase Auth/профиля и загрузка облачных личных диалогов.
- История сообщений и Realtime-подписки на сообщения.
- Редактирование и удаление сообщений.
- Реакции через таблицу `message_reactions`.
- Загрузка вложений в приватное хранилище Supabase Storage.
- Опросы в облачных чатах сохраняются в `messages.poll`; голосование проходит через серверную RPC-функцию, чтобы один аккаунт не мог одновременно голосовать за несколько вариантов.
- Непрочитанные, квитанции о прочтении, индикатор набора, presence и «был(а) в сети» (фаза 1).
- PWA: манифест, иконки, service worker, офлайн-оболочка, бейдж и фоновые Web Push.
- Пагинация истории по 50 сообщений с keyset-курсором вместо одного запроса на 1000 сообщений.

Наличие элемента интерфейса не гарантирует, что функция полностью синхронизируется между разными аккаунтами: это необходимо проверять отдельным интеграционным тестом.

## Известные ограничения, которые ещё требуют работы

- Облачные группы и ссылки-приглашения реализованы миграцией `20261028_cloud_group_chats.sql`; до её применения создание групп и вступление по ссылке не заработают.
- Приглашение добавляет пользователя в группу, роли и удаление участников доступны владельцу и администраторам (см. «Управление группами»).
- Облачные опросы требуют применения миграции `20261029_persistent_polls.sql`; локальные демо-чаты по-прежнему не синхронизируются между аккаунтами.
- Для приватных вложений используются подписанные URL сроком на час. Ссылка обновляется автоматически за пять минут до истечения (`useAttachmentRefresh`), в том числе при возврате на вкладку из фона, поэтому долго открытая вкладка больше не теряет изображения и голосовые.
- Реальная доставка фоновых уведомлений требует Edge Function `push-notify`, VAPID-ключей и Database Webhook на `messages`; звонки и игровые функции по-прежнему не серверные.

## Управление группами

Роли меняются только через RPC: все проверки иерархии живут в Postgres, поэтому обойти их правкой запроса из браузера нельзя.

| Действие | Кто может | RPC |
|---|---|---|
| Назначить или снять администратора | только владелец | `set_chat_member_role` |
| Удалить участника | владелец — любого, кроме себя; админ — только обычного участника | `remove_chat_member` |
| Покинуть группу | участник и админ; владелец — нет | `remove_chat_member` |
| Обновить ссылку-приглашение | владелец и админ | `rotate_chat_invite` |

Владелец не может снять себя или выйти из группы: сначала передай владение или удали группу. Приглашение выпускается со сроком жизни (`lifetime_hours`); после истечения код перестаёт работать, а ротация мгновенно гасит предыдущую ссылку.

## Приватность

Настройки открываются из правой панели — кнопка «Приватность и блокировки».

| Настройка | Что меняется |
|---|---|
| Скрывать «был(а) в сети» | Собеседники видят «недавно» вместо точного времени |
| Отключить квитанции о прочтении | Ты не видишь отметки о прочтении и сам их не отправляешь |
| Блокировка | Прямая переписка в обе стороны невозможна, новый чат не создать |

Блокировки проверяются в Postgres (RPC `block_user` и триггер `messages_guard_block`), поэтому обойти их правкой запроса из браузера нельзя.

Удаление аккаунта состоит из двух шагов: RPC `delete_my_account` очищает данные внутри базы (сообщения остаются обезличенными заглушками, группы передаются администраторам), затем Edge Function `delete-account` удаляет запись из `auth.users`. Service-role ключ живёт только внутри функции и никогда не попадает в браузер.

## Звонки

Голосовые и видеозвонки идут через внешний SFU — LiveKit Cloud. Собственный SFU не пишется: Supabase здесь только signaling.

| Слой | Где живёт |
|---|---|
| Состояние звонка | таблица `public.calls`, RLS видит только участник чата |
| Переходы | RPC `start_call`, `answer_call`, `end_call` — клиент не пишет `status` напрямую |
| Токен SFU | Edge Function `call-token`, подпись LiveKit JWT |
| Медиа | `livekit-client` в браузере |

Правила зашиты в базу, а не в интерфейс: звонить может только участник чата, звонивший не может ответить сам себе, двух живых звонков в одном чате не бывает, завершённый звонок нельзя оживить. Заблокированный пользователь звонок не получит — та же проверка, что и для сообщений.

### Подключение

```bash
npx supabase secrets set CALL_PROVIDER=livekit --project-ref <ref>
npx supabase secrets set LIVEKIT_URL="wss://<проект>.livekit.cloud" --project-ref <ref>
npx supabase secrets set LIVEKIT_API_KEY="API..." --project-ref <ref>
npx supabase secrets set LIVEKIT_API_SECRET="..." --project-ref <ref>
npx supabase functions deploy call-token --no-verify-jwt
```

Без `CALL_PROVIDER` функция отвечает `503 Calling is not configured`, а интерфейс показывает «Звонки пока не подключены» — остальное приложение остаётся рабочим.

Проверка живого звонка на двух аккаунтах:

```bash
node scripts/qa-call.mjs   # нужен запущенный vite preview на :4173
```

Последний прогон: **13 из 13**. Обе стороны подключаются к комнате, таймер идёт у обоих, мьют переключается, завершение доходит до собеседника и закрывает его экран. LiveKit принимает выпущенный токен (`/rtc/validate` → `success`) и отвергает подделанный (`401`).

## Мобильная обёртка (Capacitor)

PWA уже устанавливается на телефон, поэтому нативная обёртка нужна только для доступа к платформенным возможностям и публикации в сторах.

```bash
npm run cap:sync        # собирает dist в режиме mobile и копирует в android/
npx cap add android     # выполняется один раз, создаёт проект android/
npm run cap:android     # синхронизация + открытие Android Studio
```

Особенности:

- сборка `--mode mobile` использует `base: "./"`. GitHub Pages отдаёт приложение из подкаталога `/my-messenger/`, а WebView грузит файлы из корня бандла, и абсолютный префикс сломал бы все ассеты;
- `android/` и `ios/` в `.gitignore`: это генерируемые каталоги с Gradle-кэшами и ключами подписи, их место — на машине сборки;
- `server.url` намеренно не задан: удалённый URL превратил бы приложение в тонкую обёртку над браузером и сломал офлайн-режим;
- PWA service worker внутри WebView не нужен, офлайн обеспечивает сама оболочка; при этом запросы к Supabase идут по https, mixed content запрещён.

## Живая проверка на двух аккаунтах

`scripts/qa-two-accounts.mjs` прогоняет сценарий на настоящем проекте Supabase: группа, приглашение, доставка сообщения в интерфейс, роли, поиск, вложение в Storage, блокировка, настройки приватности.

Приложение предлагает только вход через Google, поэтому скрипт получает реальные сессии по паролю вне браузера и подставляет их в `localStorage` под ключом `sb-<ref>-auth-token`. Дальше всё идёт через настоящие RLS, RPC и Storage.

```bash
node scripts/qa-create-users.mjs   # создаёт двух тестовых пользователей
node scripts/qa-two-accounts.mjs   # прогоняет 20 шагов, пишет qa-results.json
```

Пароли берутся из `QA_ALPHA_PASSWORD` и `QA_BETA_PASSWORD`, служебный ключ — из `TEST_SERVICE_KEY`. `qa-accounts.json` и `qa-results.json` содержат живые токены и в репозиторий не попадают.

Последний прогон: **20 из 20 шагов**. Он же вскрыл три дефекта, которые не ловились юнит-тестами: у `service_role` не было прав на таблицы (из-за чего обе Edge-функции были неработоспособны), не было права на вызов RPC, и сами функции не были задеплоены.

## Проверки перед релизом

- Выполнить `npm run build`.
- Выполнить `npm test` — юнит-тесты доменного слоя (`src/lib/*.test.ts`).
- Выполнить `npm run test:e2e` — браузерные smoke-тесты на демо-сборке (нужен `npx playwright install chromium`). Те же шаги запускает CI-workflow `Verify` на каждый push и pull request.
- Проверить вход и регистрацию на отдельном тестовом проекте Supabase.
- Открыть приложение в двух независимых аккаунтах и проверить доставку, редактирование, удаление и реакции.
- Проверить загрузку/повторное открытие вложений после истечения подписанного URL.
- Отдельно проверить групповые чаты, приглашения и опросы после применения всех миграций.
- Проверить RLS: пользователь не должен читать сообщения чата, участником которого он не является.
- Проверить PWA: `npm run build` → `npm run preview`, установка приложения, офлайн-перезагрузка, кнопка «Загрузить ещё» на чате с 50+ сообщениями и бейдж при непрочитанных.

## Безопасность

Публичный anon/publishable key допустим в клиенте при корректно настроенных RLS-политиках. Никогда не публикуй пароли, service-role keys или другие серверные секреты.
