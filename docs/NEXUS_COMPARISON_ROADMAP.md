# NEXUS: сравнение с ведущими мессенджерами и план развития

**Дата проверки: 31 октября 2026.** Основа: репозиторий `shork-ops/my-messenger`, опубликованные изменения интерфейса и исправление аватара `aebd2df`, а также подготовленный в этой работе пакет надёжности. Документ различает выпущенные функции, подготовленный код и ещё не проверенную эксплуатацию.

## 1. Главный вывод

У NEXUS уже есть заметная функциональная база: личные и групповые чаты, каналы, медиа, поиск, реакции, опросы, папки, звонки через LiveKit и мобильная веб-компоновка. Это хорошая основа для продукта небольшой команды. Однако наличие экранов и зелёных тестов не означает равенства с крупными мессенджерами по приватности, восстановлению данных, доставке в фоне и устойчивости при нагрузке.

Ближайшая цель — сделать предсказуемыми четыре действия: найти нужного человека, отправить сообщение, получить его на другом устройстве, восстановить доступ после сбоя. Расширять развлекательные функции стоит после этого.

Рабочая гипотеза позиционирования: **лёгкий мессенджер для небольших русскоязычных групп, с понятным мобильным интерфейсом, поиском по username и управляемой инфраструктурой**. Это предложение для проверки на пользователях, а не установленное конкурентное преимущество.

## 2. Метод сравнения

Выбраны шесть ориентиров с разными сильными сторонами: Telegram, WhatsApp, Signal, Discord, Element/Matrix и iMessage. Они не ранжированы по популярности: задача — выбрать полезные продуктовые и инженерные практики, а не объявить единственного победителя.

Факты о конкурентах проверены по официальным страницам, перечисленным в разделе 17. Региональная доступность, платные тарифы, точные лимиты участников и файлов не используются как постоянные величины: они меняются и требуют отдельной проверки перед конкретным решением.

Для NEXUS применена шкала доказательств:

| Уровень | Что действительно подтверждено |
|---|---|
| L0 | Функция отсутствует или есть только идея |
| L1 | Код/экран существует |
| L2 | Есть модульная или локальная серверная проверка |
| L3 | Сценарий проходит в браузере; деморежим отмечается отдельно |
| L4 | Проверено на двух реальных аккаунтах с рабочим backend |
| L5 | Проверено на физических Android/iOS, в фоне и при плохой сети |

Тесты браузера в деморежиме нельзя выдавать за L4/L5. Проверка SQL на PostgreSQL-фикстуре также не подтверждает настройки рабочего Supabase Storage, расписания функций или push-службы.

## 4. NEXUS относительно этих ориентиров

| Область | Состояние NEXUS по коду | Вывод для развития |
|---|---|---|
| Личные чаты | Создание через RPC, профиль и история; исправлена потеря пути к аватару | Нужна идентичность по UUID во всех путях, а не по имени |
| Группы | Есть участники и роли, RPC управления | Проверить обход ролей прямыми запросами, гонки смены владельца и удаление аккаунта |
| Каналы | Есть роли автора/подписчика и ограничения интерфейса | Подтвердить серверное запрещение записи подписчику на рабочей базе |
| Текст и реакции | Есть редактирование, ответы, форматирование, реакции | Отдельно проверить сохранение метаданных ответа и идемпотентность каждой операции |
| Поиск | Есть поиск пользователей и серверный поиск сообщений | Оценить индексы, скорость и запрет выдачи чужой истории |
| Медиа | Загрузка, сжатие, миниатюры, голосовые, видео, альбомы | Исправлять доставку/повтор/очистку, прежде чем увеличивать лимиты |
| Одноразовые фото | Раньше факт просмотра жил в localStorage; теперь подготовлен серверный путь | Для рабочего включения нужны SQL и Edge Function; уже полученные копии нельзя отозвать |
| Доставка | Подготовлены устойчивые UUID, outbox, ошибка и повтор для текста/стикеров | «Принято сервером» не равно «доставлено на устройство»; нужны честные отдельные состояния |
| Аватары | Подготовлены продление ссылки и обновление профиля | Проверить смену/удаление фото из второй сессии и после сна телефона |
| Мобильный интерфейс | Полноэкранный чат, нижняя навигация, компактная шапка, жесты | Нужен отдельный прогон с системной клавиатурой и safe area физических устройств |
| Звонки | Есть LiveKit, состояния звонка, камера и экран | E2EE LiveKit требует явного включения и безопасного распределения ключей; наличие SDK этого не доказывает. [Документация](https://docs.livekit.io/transport/encryption/) |
| Аккаунты | Есть Google OAuth, TOTP-компоненты и локальные слоты аккаунтов | Проверить обязательность второго фактора сервером и управление реальными сессиями |
| Данные | Есть клиентский экспорт/архив | Экспорт не равен проверенной резервной копии БД и файлов с восстановлением |
| Игры | Есть отдельные игровые поверхности | Приглашение в игру содержит заглушку; сетевой совместный режим нельзя считать завершённым |
| Эксплуатация | Есть GitHub Pages, проверки и интеграция мониторинга | Настройки production, резервирование и реагирование на сбои не подтверждены доступом к коду |

## 5. Плюсы вашего мессенджера

### Уже полезные свойства

1. **Узнаваемый визуальный стиль.** Тёмная тема и жёлтый акцент позволяют сохранить собственный характер. Не требуется заново проектировать все экраны.
2. **Широкая основа общения.** Чаты, группы, каналы, файлы, голосовые и поиск уже имеют кодовые пути. Развитие можно вести вокруг ежедневного использования, а не создавать всё заново.
3. **Быстрый вход через веб.** Пользователь может начать с ссылки; установка приложения не является обязательным первым шагом.
4. **Поиск по username.** Публичный номер не встроен в клиентский сценарий знакомства как обязательный идентификатор контакта. При этом зависимость от Google-входа остаётся отдельным ограничением.
5. **Серверные правила существуют.** Часть ограничений, включая блокировку личных сообщений, реализована в PostgreSQL, а не только скрытием кнопок.
6. **Компоненты тестируемы.** Есть модульные и браузерные тесты. Они помогают ловить регрессии при изменении интерфейса и логики.
7. **Контролируемая архитектура.** Собственный исходный код, явные миграции и отдельные Edge Functions дают возможность разбирать причины ошибок и менять поведение.
8. **Есть работа с большими историями.** Пагинация и виртуализация полезнее для повседневной скорости, чем декоративные функции.

### Что пока является гипотезой, а не доказанным преимуществом

Нельзя утверждать, что NEXUS быстрее, дешевле, безопаснее или удобнее названных конкурентов: нет одинаковых замеров на одних устройствах, производственных метрик и независимого аудита. Эти утверждения можно проверять по методике ниже.

## 6. Минусы и риски NEXUS

1. **Нет подтверждённого сквозного шифрования содержимого чатов.** TLS, RLS и приватный bucket решают другие задачи. Серверное хранение открытого текста не соответствует модели, в которой оператор не может читать переписку.
2. **Жизненный цикл аккаунта проверен слабее интерфейса.** Нужно отдельно тестировать вход, второй фактор, выход со всех устройств, восстановление и удаление аккаунта вместе с файлами.
3. **Надёжность общения ещё формируется.** Сам факт успешного SQL INSERT не подтверждает получение другим устройством. Потеря ответа сервера и повторная отправка требуют устойчивой идентичности операции.
4. **Есть зависимость от нескольких внешних компонентов.** Supabase, Google OAuth, LiveKit и браузерные push-службы имеют разные состояния отказа. Интерфейс должен объяснять, какая часть недоступна.
5. **Проверки в деморежиме могут создавать ложное чувство завершённости.** Они не проверяют рабочие политики, токены функций, реальные уведомления или мобильный фон.
6. **Крупный useMessenger затрудняет изменения.** В одном месте сосредоточены разнотипные операции. Разделять его лучше по операциям с устойчивыми контрактами, а не переносом строк между файлами.
7. **Модерация и антиспам недостаточно оформлены.** До публичного привлечения пользователей нужны ограничения частоты, жалобы и процедура обработки, иначе маленькая команда быстро столкнётся со злоупотреблениями.
8. **Не доказана эксплуатационная готовность.** Нужны проверенное восстановление, квоты хранилища, мониторинг с ограничением персональных данных и понятный владелец инцидента.
9. **Возможности разных платформ неравнозначны.** Успешный desktop viewport не подтверждает работу iOS PWA, системных разрешений и звонков в фоне.
10. **Функциональная широта обгоняет глубину.** Есть много поверхностей, но некоторые пути остаются локальными или требуют внешней настройки.

## 7. Что перенять у каждого ориентира

### Telegram: цельная облачная история

Урок для NEXUS — одинаковая идентичность диалога, стабильное восстановление истории, ясная граница локальных и облачных данных. Выход/вход и смена устройства не должны создавать «второго» собеседника из-за одинакового имени. Сама облачная синхронизация не должна называться E2EE. Различие облачных и секретных чатов Telegram явно описано в его [политике приватности](https://telegram.org/privacy).

### WhatsApp: простые повседневные действия

Полезно измерять количество действий от запуска до ответа и сделать состояния отправки понятными без документации. Для одноразового медиа важно отдельно объяснять ограничение доступа и невозможность гарантированно предотвратить сохранение внешней камерой. Даже официальный [справочник WhatsApp](https://faq.whatsapp.com/1077018839582332) сохраняет это ограничение.

### Signal: идентичность и приватность должны быть объяснимыми

Нужно разделять username, отображаемое имя и неизменяемый ID; одинаковые имена не должны менять адресата. Для будущего E2EE потребуется проверка устройств и собеседника, а не декоративный значок замка. Пользовательский сценарий восстановления также нужно проектировать заранее: Signal документирует отдельные [варианты резервирования и переноса](https://support.signal.org/hc/en-us/articles/10074659364122-Backups-and-Device-Transfers-on-Signal).

### Discord: сообщества требуют инструментов управления

Канал и группа — разные роли и ожидаемое поведение. Для крупных сообществ понадобятся жалобы, очередь модерации, журнал действий, ограничения скорости и понятные права. Наличие чата с несколькими ролями ещё не даёт зрелой модерации. Официальный [FAQ AutoMod](https://support.discord.com/hc/en-us/articles/4421269296535-AutoMod-FAQ) полезен как перечень типов задач, а не как требование немедленно копировать автоматическую фильтрацию.

### Element/Matrix: управляемость данных

Полезны открытые контракты, экспорт в документированном формате и воспроизводимое развёртывание. Федерация — отдельная архитектурная задача: собственная инсталляция Supabase не делает NEXUS совместимым с Matrix. При будущем E2EE надо соединить удобство входа с реальным сохранением ключей. [Документация Element](https://docs.element.io/latest/element-support/matrix-account-management/securing-a-matrix-account/) показывает, почему восстановление — часть продукта.

### iMessage: интерфейс использует возможности устройства

Урок — аккуратная работа с клавиатурой, системными разрешениями, уведомлениями и идентичностью контакта. Верификация должна сообщать пользователю о реальной проверке ключей. В NEXUS нельзя имитировать [Contact Key Verification](https://security.apple.com/blog/imessage-contact-key-verification) без соответствующего протокола.

## 8. Приоритеты и критерии выбора

Предлагаемые веса для ближайшего этапа: надёжность 25%, безопасность 25%, мобильное удобство 20%, данные/несколько устройств 10%, звонки 10%, эксплуатация 10%. Это рамка принятия решений, а не вычисленная оценка продукта.

Сначала выполняется задача, которая предотвращает потерю данных или доступ постороннего. Затем — задача, которая мешает первому разговору и ежедневному ответу. После — удобства и рост аудитории. Новые публичные обещания добавляются только после проверки соответствующего backend-сценария.

Обозначения: **A** — можно реализовать в коде и проверить автономно; **B** — нужен рабочий доступ Supabase/инфраструктуры; **C** — требуется физическое устройство, внешний аудит или длительный эксплуатационный замер.

## 10. Что уже делается автономно

Подготовленный до этого документа пакет покрывает R01–R08, R10–R11 на уровне кода и локальных проверок, с важной оговоркой: R05–R08 не становятся рабочими в Supabase от одного деплоя GitHub Pages. Команда серверного развёртывания и ограничения описаны в `docs/RELIABILITY_ROLLOUT.md`.

Первые исправления нового пакета: идентичность по UUID; устойчивые UUID сообщений; отдельный outbox пользователя; статусы и повтор для текста и стикеров; продление ссылок аватаров и обновление профиля; проверка maintenance-токена; сохранение ссылок на файлы альбомов при cleanup; серверные receipts и отдельное хранилище single-view.

Сразу после сохранения этого плана выполняется следующий небольшой пакет **R09, R12–R14**: fail-closed production-конфигурация, индикатор сети, проверка длины текста и единый список файлов. Он улучшает понятность продукта, не требует покупки сервисов и не меняет модель доступа к чужим данным.

## 11. Дорожная карта по этапам

### Этап A — устойчивое ядро

Завершить текущие исправления и развернуть серверные функции после восстановления доступа. Обязательные критерии: один диалог на нужного человека, один результат повторной операции, восстановление неотправленного сообщения, отсутствие прямого доступа к одноразовым файлам, защищённый cleanup. До приёмки этих критериев single-view не рекламируется как полностью включённый.

### Этап B — доверие к аккаунту и данным

Проверить изоляцию кэша, второй фактор, сессии, отзыв устройства, удаление аккаунта и восстановление после сбоя. Здесь опасно оценивать успех по наличию переключателя в настройках: каждый пункт проверяется прямым API и второй сессией.

### Этап C — ежедневное мобильное использование

Пройти реальные сценарии клавиатуры, разрешений, фона, уведомлений и слабой сети. Измерить ответ из уведомления, время до первого сообщения, длину пути к файлу и восстановление после потери сети. Упростить только те элементы, которые мешают этим действиям.

### Этап D — безопасность публичного роста

Добавить rate limits, защищённые жалобы, журнал модерации, управление квотами, мониторинг и процедуру реагирования. Начинать с правил и ручной очереди, которую можно обслуживать; автоматическая модерация без процесса не закрывает задачу.

### Этап E — приватность и расширение продукта

После модели угроз выбрать путь E2EE и восстановления ключей. Только затем решать вопрос федерации, интеграций, ботов и сетевых игр. Эти направления меняют архитектуру и не должны добавляться как непроверенные «галочки».

Оценки сроков следует делать после A и B: неизвестны рабочие настройки Supabase, бюджет, целевая нагрузка и доступность устройств. Приравнивать объём исходников к оставшемуся времени разработки неправильно.

## 12. Матрица приёмки для двух аккаунтов

| Сценарий | Действие | Обязательный результат |
|---|---|---|
| Одинаковые имена | A/B выбирают одно имя, C ищет username B | Открывается B по UUID, не A |
| Новый аккаунт | C создаёт диалог с A с фотографией | Фото видно сразу, без повторного входа |
| Смена фото | A меняет/удаляет фото, B остаётся в чате | B получает новое состояние без устаревшего изображения |
| Потеря ответа | INSERT принят, ответ потерян, клиент повторяет | Одна строка и одно сообщение у B |
| Перезапуск offline | A отправляет, получает ошибку и перезапускает страницу | Неотправленное доступно A; B в другом слоте его не видит |
| Single-view | A отправляет B, B открывает с устройства 1 | Устройство 2 того же B не получает новую выдачу |
| Посторонний | C знает ID сообщения/путь файла | Нет права чтения, подписи ссылки или сброса receipt |
| Удаление | A прерывает удаление между шагами и повторяет | Состояние объяснимо, повтор безопасен, файлы учтены |
| Блокировка | B блокирует A, A обходит UI прямым INSERT | Сервер отказывает согласно выбранной политике |
| Звонок | Потеря сети, возврат, завершение | Нет скрытой записи или оставшихся локальных tracks |
| Фон | Телефон блокируется, приходит сообщение | Уведомление соответствует настройкам, read не ставится раньше просмотра |

## 13. Метрики и целевые значения

Ниже — предлагаемые критерии, а не уже измеренные результаты NEXUS.

- **Потеря/дубли:** ноль дублей в тесте повторной операции; ноль исчезнувших подтверждённых сообщений в заданном стенде. Отдельно считать отказ, повтор и принятие сервером.
- **Отправка:** p50/p95 от нажатия до серверного подтверждения при фиксированных условиях сети. Не смешивать это с получением вторым устройством.
- **Доставка:** p95 до появления у второго клиента при активном Realtime и после восстановления соединения. Цель задаётся после первого базового измерения.
- **Восстановление:** измеренные RPO/RTO для БД и Storage; фактическое восстановление в отдельный проект, а не только наличие настройки backups.
- **Мобильный UX:** первый разговор, ответ, вложение и блокировка проходят без горизонтального скролла при 320/390/430 px; на реальном устройстве клавиатура не перекрывает ввод.
- **Доступность:** интерактивные элементы доступны клавиатуре и диктору; изменение масштаба текста не скрывает отправку/возврат; контраст измеряется, а не оценивается только визуально.
- **Безопасность:** отрицательные тесты на чужой чат, чужой bucket, отозванный доступ, закрытый endpoint и повтор single-view.
- **Эксплуатация:** доля ошибок с известной причиной, время обнаружения, время восстановления и число повторов инцидента.

Собирать данные о времени и результате операции можно без тела сообщения, списка контактов, токенов и фотографий. Уникальные идентификаторы событий должны иметь срок хранения и назначение.

## 14. Производительность и стоимость

Сначала собрать базу: активные пользователи, сообщения/день, средний размер медиа после сжатия, объём скачивания, минуты звонков и среднее число участников. Затем оценивать:

`затраты ≈ БД + хранение + исходящий трафик + функции + медиа-звонки + мониторинг + резервирование`.

Увеличение лимита файлов или участников без этих измерений может увеличить стоимость и ухудшить качество. Не предлагается покупать тарифы или менять поставщика вслепую. Квоты и ограничения должны иметь объяснимый пользовательский ответ, а не молчаливое падение операции.

Для фронтенда важно измерять стартовый набор JS отдельно от лениво загружаемого LiveKit. Предупреждение о большом чанке само по себе не доказывает медленный первый запуск, но требует проверки waterfall и условий загрузки.

## 15. Архитектурные решения, которые нельзя заменить косметикой

### E2EE

Нужны идентичности устройств, ключи, их проверка, смена состава группы, отзыв устройства, восстановление, поиск и формат хранения вложений. Использовать готовый протокол и проверенные библиотеки; не изобретать собственный шифр. Серверный ключ, доступный оператору, не обеспечивает нужной модели угроз. Отдельно решить, какие сведения остаются метаданными и кто их видит.

### Восстановление

Определить, что произойдёт при утрате всех устройств и ключей. Удобство восстановления и приватность должны быть описаны до релиза, а не после первой потери истории. Механика резервирования у разных продуктов различается, поэтому обещание «как у всех» неприемлемо.

### Несколько устройств

Слот аккаунта в одном браузере — не реестр доверенных устройств. Требуется реальная серверная модель сессии, срок действия, отзыв и проверка второго клиента. Для зашифрованной истории добавляется распределение/проверка ключей.

### Одноразовый доступ

Сервер может ограничить новую выдачу файла, но не уничтожить ранее сохранённые байты. Текущий проект намеренно сохраняет это различие. Короткий TTL не заменяет receipt, а receipt не заменяет приватную Storage-политику: нужны оба механизма.

## 16. Релизный процесс

1. Записывать проблему, изменение поведения и негативный сценарий, который должен перестать работать.
2. Выполнять build, модульные тесты, серверные проверки и браузерный прогон.
3. Отдельно отмечать, использовался ли demo, локальный PostgreSQL, staging или production.
4. При серверных изменениях проверять совместимость старого клиента и миграций; при отсутствии backend-поддержки отказывать безопасно и понятно.
5. После деплоя проверять фактическую версию страницы и обновление PWA-кэша. Зелёный git push не равен опубликованному сайту.
6. Иметь понятный откат клиентского коммита и отдельный план для SQL, не удаляющий подтверждённые сообщения и receipts.
7. Не объединять обновление интерфейса с неподготовленным изменением ключей, авторизации или структуры истории.
