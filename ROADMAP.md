# Nexus Messenger — план развития

Составлен 2026-10-28 по коду коммита `f55927e` и сравнению с Telegram, WhatsApp, Signal и Discord.

## 1. Текущее состояние

### Работает

- Google OAuth, профиль: `display_name`, аватар-буква, уникальный `username`.
- Личные диалоги через `create_direct_chat`, группы через `create_group_chat` и вход по invite-коду.
- Сообщения: текст, вложения до 50 МБ в приватном bucket, эффекты, ответы, правка, soft-delete, реакции, @упоминания, опросы.
- Realtime-подписки на `messages` и `message_reactions`.
- Опросы с серверной защитой от повторного голосования (`vote_on_poll`) и защитой от подмены голосов триггерами.

### Отсутствует или носит декоративный характер

| Возможность | Факт |
|---|---|
| Квитанции прочтения | `CheckCheck` в списке чатов — иконка (`src/App.tsx:833`); колонка `chat_members.last_read_at` (`supabase/schema.sql:28`) не используется ни разу |
| Индикатор набора текста | нет |
| Presence / «был(а) в сети» | нет |
| Push и уведомления | PWA-оболочка, бейдж и локальные уведомления есть; фоновые Web Push готовы в коде, но требуют VAPID-ключей и деплоя Edge Function |
| Пагинация истории | Keyset по 50 сообщений с подгрузкой при скролле |
| Поиск по истории | только по загруженным сообщениям активного чата (`src/App.tsx:133`) |
| Голосовые сообщения | запись есть, но сообщение не уходит в БД (`src/App.tsx:576`) |
| Управление группой | нет ролей и удаления участников, invite не отзывается |
| Приватность | нет блокировок, жалоб, скрытия статуса, исчезающих сообщений |
| Звонки, E2EE | нет |
| Тесты, мониторинг | тестов нет; CI на `main` — только деплой |

## 3. Выводы

1. Основной разрыв — не в функциях, а в петле доставки: нет ответа на вопросы «мне пишут?», «прочитали?», «человек здесь?». Без этого даже исправно работающий чат ощущается мёртвым.
2. Сильные стороны недооценены: защита голосов в опросах, приватный Storage с проверкой членства и RLS-харденинг — уровень выше среднего для проекта такого размера.
3. Догонять Telegram по каналам, ботам и платежам для одного разработчика — тупик. Догонять нужно базовую петлю, а отличаться — тем, что уже есть.
4. E2EE — не задача на месяц: Signal-протокол или MLS требуют человекомесяцев. Честнее не заявлять E2EE, чем сделать его плохо.

### Фаза 2 — Полноценный чат (12–18 дней)

1. **Управление группами**: RPC на смену роли, приглашение и удаление участника администратором, ротация и срок жизни invite. Закрыть два известных нюанса: `admin` может снять `owner`, а `chats_update_admin` позволяет менять `created_by`.
2. **Серверный поиск**: `tsvector` и GIN-индекс, RPC `search_messages(chat_id, query)` с проверкой членства, подсветка совпадений.
3. **Пересылка, закреплённые сообщения, избранное.**
4. **Медиа**: сжатие и превью на клиенте, галерея чата, прогресс загрузки, очистка осиротевших файлов.
5. **Голосовые сообщения по-настоящему**: файл в Storage, `attachment` в сообщении, waveform-плеер.
6. **Приватность**: блокировка пользователя, скрытие «был(а)», учёт отключённых квитанций, удаление аккаунта с очисткой данных.

Критерий: Playwright-сценарий «два аккаунта, группа, роли, поиск, вложение, блокировка» проходит в CI.

**Статус: все шесть пунктов закрыты, критерий выполнен на живом проекте.**

Демо-прогон в CI (`tests/e2e/phase2.spec.ts`) покрывает клиентскую часть: две независимые вкладки, группа со ссылкой-приглашением, открытие поиска, вложение и модалку блокировок. Секретов в CI нет намеренно.

Настоящая проверка на двух аккаунтах сделана отдельно через `scripts/qa-two-accounts.mjs`: **20 шагов из 20** на реальном Supabase — группа, вступление по инвайту, доставка сообщения в интерфейс, повышение до администратора, запрет админу снимать владельца, серверный поиск, загрузка вложения с подписанным URL, блокировка и разблокировка, настройки приватности, триггер блокировки в обход RLS.

Эта проверка вскрыла три дефекта, которые не ловились ни юнит-, ни демо-тестами, и они исправлены в миграциях `20261038`–`20261039`: у `service_role` не было прав на таблицы (обе Edge-функции были неработоспособны), не было права на вызов RPC, и сами функции не были задеплоены.


### Фаза 3 — Дифференциация (4 и более недель, по желанию)

- **Звонки 1:1 и групповые**: LiveKit Cloud или Cloudflare Calls, Supabase — только signaling. Собственный SFU не писать.
- **E2EE**: либо не заявлять вовсе, либо 1:1 на проверенной библиотеке. Самостоятельный double ratchet на WebCrypto — почти гарантированный баг.
- **Мобильное приложение**: Capacitor-обёртка вокруг PWA.
- **Каналы, threads, боты** — только при появлении аудитории, которой это нужно.

**Статус на момент закрытия фаз 0–2:**

| Пункт | Решение |

| E2EE | Не заявляется. Честнее, чем частичное шифрование: серверный поиск и тексты пуш-уведомлений остаются рабочими. |
| Каналы, threads, боты | Отложены по собственному правилу роадмапа. На момент проверки в проекте 2 пользователя, 1 чат и 16 сообщений — аудитории, которой это нужно, ещё нет. Вернуться, когда появятся метрики удержания D1/D7. |

## 5. Порядок, метрики, риски

**Порядок:** Фаза 0 → Фаза 1 → Фаза 2. Внутри Фазы 1: непрочитанные → уведомления → набор → presence → пагинация → PWA. Это порядок влияния на удержание, а не сложности.

**Не делать сейчас:** каналы, боты, платежи, магазины стикеров, светлая тема, i18n, собственный E2EE, собственные звонки.

**Метрики:** время от открытия до первого отправленного сообщения, удержание D1/D7, p95 загрузки истории, доля сообщений, прочитанных в течение минуты, число JS-ошибок на сессию.

**Риски:** free tier Supabase ограничивает Storage и число Realtime-соединений — push и медиа упрутся быстро; GitHub Pages не умеет SPA-fallback, поэтому маршруты держим на hash; после фаз 1–2 один проект Supabase станет узким местом для звонков, их лучше выносить сразу.
